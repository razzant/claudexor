An Antigravity (`agy`) try that fails with the vendor's own stderr record `AGY_ERROR: {...}` saying exactly `"retryable": false` now ends the run instead of continuing it: the try carries the typed `vendor_not_retryable` request refusal (`source: agy_stderr`, with the record's `error_id`), so there is no retry, no in-run continuation on the same native session and no move to another account, also after progress. The run fails with category `harness_error` and code `vendor_not_retryable`; its streamed text stays retained evidence and its next actions name the vendor's error id. Only the vendor's stderr line counts, and only its explicit boolean in the try's last line with the `AGY_ERROR: ` marker: a later unreadable record leaves the verdict unknown, while stderr lines without the marker do not change it. `retryable: true`, a missing or non-boolean field, malformed JSON, the minimal `short_error`-only form, the same words in model text and a warning a session continued past keep today's behavior, including the existing continuation after an error without a typed cause. This does not establish why the vendor refused a request. A refused try now settles like every other try before the attempt stops: after progress the failed run still lists the `packet` carrier, so an explicit `continueFrom` re-briefs from its evidence instead of starting fresh, and its `resumable` cause is `other` rather than an earlier try's `transport`. Earlier request refusals (Codex input, Grok credential source) skipped that settlement too; the new refusal after progress exposed it.
