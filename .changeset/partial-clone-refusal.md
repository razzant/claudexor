An isolated run no longer starts in an incomplete copy of a partial or sparse clone (#501). When the base commit has files whose content the repository never fetched (a blobless clone's older commit, or files a sparse checkout of one left out), Git's checkout of the private copy reported each file and still succeeded, so the run began with those files missing and its result could read as deleting them. The run now fails in its workspace phase before anything starts, naming the files and the two ways forward: make that content present (a complete clone, or `git sparse-checkout disable` in a sparse checkout), or run in place in that folder (`--in-place`, or an in-place thread). Claudexor fetches nothing, and the folder's files, index and refs stay as they were. A delivery's fresh verify applies the same rule, so it can no longer report a result as checked on such an incomplete copy. Partial and sparse clones whose files are all present keep working as before. A shallow partial clone that Git itself cannot copy (a sparse checkout of a shallow blobless clone, or a deeper shallow blobless clone whose older commits' content was never fetched) used to fail with Git's report of an unreadable object and "possible repository corruption"; its refusal now keeps Git's full report first and adds, as an observation that does not prove the cause, the base commit's files the source lacks, or how many objects its branches and tags reach, with the same two ways forward. Other clone failures keep Git's report alone. An envelope refused this way never started, so it is removed by the call that created it rather than left behind for the daemon's lifetime; if that removal fails, the refusal stands and its message says what was left.
