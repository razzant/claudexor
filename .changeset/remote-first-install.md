`claudexor remote preflight <ssh-destination> --json` and `claudexor remote install <ssh-destination> --digest <sha256> --json` install this CLI's signed SSH runtime on an empty server the person confirmed. The destination is parsed before any SSH call: a `Host` alias or host name, `user@host`, or `ssh://[user@]host[:port]`, IPv6 included (an IPv6 zone only bare, not inside `ssh://`); another login form goes into `User` of a trusted `Host` alias. The preflight only reads and shows the SSH login, the server's host key fingerprints and the offered build; an installed runtime is identified from its own metadata files, never run. A manifest that could not be read whole is reported as unavailable, not as unverified, and a runtime file that could not be read leaves the host blocked as `runtime_unreadable`, never a mismatch. The install writes only to a server that proves those host keys, in one writing step that first proves the confirmed hostname, platform, user, uid and home, and in which the shared install transaction itself receives the signed archive into its own file and removes it on an ordinary end. It uses its own directory and runtime pointer, starts no daemon or login, and ends with a read-only identity check. Connecting stays the separate `remote bootstrap`. An installed, unknown or locked runtime is never changed. An answer says `activated: false` only where that is proven: before the writing step, on its recipient refusal, or on the transaction's own refusal. Any other outcome the client did not see, a broken stream included, is reported as unknown with what a later preflight must show, and is never retried. These commands need OpenSSH 8.5 or newer and check host keys against known-hosts files only, loopback included, without adding to them or sharing a connection. The macOS app runs the same shared install and rollback scripts. Both now release only their own lock, once, also when their output stream breaks or a signal arrives, so a dropped connection no longer leaves the lock that blocked the app's next install or rollback. A lock directory they cannot create (no space or no permission) is now a failure with exit 73 and the system's reason, no longer taken for another install's lock. The install script also prints a receipt after activation or a refusal before it, keeps a directory it already moved into place, and asks for a lock to be removed by hand only after checking that no install still runs.
